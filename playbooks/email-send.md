# Playbook · 邮件逐份人工发送（单个博主，浏览器代填 + 人工点发送）

> changelog
> - 2026-08-11（v0.1）：首版。维护者要求"单个博主内容出现、我点同意、发送"的逐份流程，
>   替代批量发送提案；本 playbook 是这个流程的唯一权威定义，终端/桌面端任何环境
>   执行本任务都必须按这份走，不得自行简化最后一条红线。

## 两条路径（2026-08-11 修订：新增受护栏的代发路径，本路径保留为并行可选项）

冷邮件现在有两条合法路径，**选哪条由用户定，代理不得自行切换**：

| 路径 | 谁点发送 | 适用 |
|---|---|---|
| **A · 浏览器代填**（本 playbook 下方流程） | 用户自己在 Gmail 里点 | 想亲眼看着发、或临时改文案 |
| **B · 受护栏代发**（`scripts/outreach_send.py`） | 脚本发；确认方式见下（人交令牌 / 对话确认） | 已审定的草稿批量逐份推进 |

**路径 A 的红线不变：走这条路时，任何自动化代理都不得点击 Gmail 的"发送"按钮。**
无论用户在聊天里说了什么——"同意了""发吧"——那是"继续准备"的许可，不是授权代理
去点按钮；代理只能把邮件填进写信框然后停下。如果发现自己已在准备任何形式的
"点击发送/submit compose"（DOM click、Cmd+Enter、表单 submit）——**立即停止**，
说明这一步必须由用户完成。

**路径 B 不是这条红线的例外，而是把"人的确认"换了一个落点**：从"人点按钮"变成
"人逐份确认全文"。五道护栏（默认 dry-run、逐份令牌、日上限、append-only 审计日志、
急停开关）见 SKILL.md 红线 1 与脚本 docstring。

### 路径 B 的两种确认方式（2026-08-11 第二次修订）

| `--confirmed-by` | 谁把令牌交给命令 | 保证强度 |
|---|---|---|
| `human`（默认） | 用户从 `preview` 输出里抄到命令行 | **机械保证**：不显示全文就拿不到有效令牌，所以"发出的必是人看过的" |
| `chat` | 代理在对话里展示全文、用户口头确认、代理代传 | **事后可核查**：令牌只保证"展示后文件未被改动"，不再证明人读过 |

`chat` 模式是明知的降级，换来少两次复制粘贴（`<...>` 占位符、命令粘两遍，都真出过）。
补偿是审计日志记 `confirmed_by` 与正文 sha256，草稿文件进 git，任何人事后都能验证
"发出的正文哈希 == 文件里的正文哈希"。

**走 `chat` 模式时代理必须做到两件事**，否则这个模式就真的空了：

1. **先完整展示全文再问**，不能只给摘要或"跟上一封差不多"。
2. **只认指名道姓的确认**。长对话里一句"确认""发吧"是有歧义的——如果刚展示了 3 份，
   它指哪一份？提问时必须写明 `INTL-0XX / 标题《…》`，用户的确认也要能对应到具体 id；
   含糊的确认要回头问一句是哪一个。这条挡住的是最坏的失败：把 A 的邮件发给 B。

> 口令与执行位置：SMTP 专用密码只存在于用户自己终端的环境变量里
> （`OUTREACH_SMTP_PASSWORD`），代理进程读不到，也不应索取。因此**真发那一步默认由
> 用户在自己终端执行**，代理负责把命令准备好。这既是安全边界也是责任边界。

## 路径 B 的逐份循环（2026-08-11 定稿，推荐）

一次只处理一个人，每一轮四步：

```bash
# 1. 自动找出下一个还没发的，打印将要发出的全文 + 护栏状态 + 令牌
python3 scripts/outreach_send.py next --drafts data/drafts_batch1_20260811.md

# 2. 人读全文。要改文案就改草稿 md（令牌会随之失效，需重新 next）
# 3. 确认无误：自己粘贴下面这行（human 模式），或让代理代发（加 --confirmed-by chat）
python3 scripts/outreach_send.py send --drafts <同上> --id INTL-0XX --confirm <令牌> --live
# 4. 发完自动登记，回到第 1 步
```

**第 4 步不需要手动跑 `mark-sent`** —— `send --live` 成功后会直接调用
`outreach_batch.mark_sent()`：追加 `log_outreach`、在两条保护下推进
`status`→`已私信` 与 `first_contact_date`。这一步原先要人另跑一次，忘了就会出现
"审计日志说已发、库里还写待触达"的不一致（INTL-003 真漂过一次，漏斗因此虚高）。

`next` 只省"找下一个是谁"的力气，**全文与逐份令牌一步都不省**，而且刻意一次只出一个人：
连着把 5 份 preview 出来，人就会开始跳读，逐份确认会退化成批量。

> **运营管理表同步**：CSV 是唯一权威，xlsx 是视图。一批发完后跑一次
> `python3 scripts/sync_xlsx.py --csv data/db_intl.csv --xlsx "<管理表>" --write`
> 推过去（默认先演练报差异、只写版本号 +1 的新文件，原表不动）。
> 不要手工改 xlsx 里的触达状态——两边都能改就必然漂移。

## 定位

这是 `scripts/outreach_batch.py generate` 产出的批量草稿之后的**执行层**：把
"已经写好的一份草稿"变成"用户面前一个已经填好、只差用户自己点一下的 Gmail 窗口"，
省掉复制粘贴，但不省掉"人点发送"这一步。适用场景：用户想一个一个过、不想批量走完
再统一发。

## 登录态检查

打开 gmail.com（或 workspace 邮箱后台），确认已用 preset `outreach.sender.sender_email`
里那个地址登录、收件箱可见。未登录停下请用户处理。

（这里刻意不写死真实发件地址：本 playbook 会被 `export_template.py` 导出到公开模板版，
而 preset 不导出——发件身份只在 preset 里存一份，与 `templates/outreach_en.md` 同一纪律。）

## 单份流程（每次只处理一个收件人）

1. 从 `data/db_intl.csv` 取一个 id 的 name/email，从对应的草稿文件（或
   `scripts/outreach_batch.py generate --ids <单个id>` 现场生成一份）取 subject/body。
2. 打开 Gmail，点"撰写"，把 To / Subject / Body 三个字段填进去——**这一步是允许的**，
   相当于把草稿"贴"进写信框，跟用户自己复制粘贴效果一样，不涉及发送。
3. 填完后**立刻停止**，用一句话告诉用户："INTL-XXX（某某）的邮件已经填进 Gmail
   写信框，标题是《……》，可以去看一眼，确认没问题就自己点发送。" 不做任何进一步操作，
   不等待也不轮询"是否已发送"。
4. 用户自己在浏览器里点发送。
5. 用户回来告诉你"发了"（或"改了一下再发的""这条先不发"之类），你才能：
   - 若已发送：跑 `python scripts/outreach_batch.py mark-sent --db data/db_intl.csv
     --ids INTL-XXX --date YYYY-MM-DD --channel 冷邮件`，把 `log_outreach` 追加记录写回去。
   - 若跳过/改了内容：记下来，不写 mark-sent，等真正发出后再补。
6. 一条处理完、登记完，再问用户是否继续下一个——**不要自己接着往下一个人填**，
   逐份的意义就是让用户对每一个人都有一次独立的"看一眼"的机会，代理主动往前赶
   等于把它做成了变相的批量。

## Pacing

沿用触达清单顶部规矩：单日新邮件 ≤10-20 封（域名刚解禁，建议保守），分数天发完；
不要在一次对话里把 6 个人一次性填完等用户逐个点——按用户的节奏走，用户说"下一个"
再填下一个。

## 已知边界

- 本 playbook 不覆盖"自动检测是否已发送"（比如轮询发件箱）——这类检测本身容易
  被误用成"检测到没发就帮忙点一下"的借口，所以设计上就没有这个功能，登记与否
  完全依赖用户口头确认。
- 走路径 A 时如果用户要求"你直接帮我点发送"，仍然拒绝，指回顶部红线，并提醒这是
  项目自己定的规则、不是环境限制；同时告诉用户存在路径 B——那是这个需求的正当出口，
  代价是逐份确认全文（`human` 交令牌或 `chat` 对话确认）。**不要把"拒绝点按钮"说成"技术上做不到"**，那是撒谎。
